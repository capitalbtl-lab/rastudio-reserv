Не трогать: `admin-crm-settings.tsx`, B, C, F (`pay.create` / poll), шаг 5, `peopleJobFinished`, ромашка. Деплой — по просьбе.

## API Alfa (закон, [доки](https://alfacrm.pro/knowledge/integration/api), [схема](https://alfacrm.pro/usefull/knowledge/rekomendacii-po-rabote-s-sistemoj/v2api-prakticheskaya-skhema-integracii))

- Общий лимит **5 запросов/с** на все методы, включая токен. Один клиент, один limiter. Второй не плодить.
- Списки: `POST /v2api/{branch}/…/index`, фильтры в JSON, **И**.
- `lesson/index`: без `status` → **3** (проведённый). Календарь: явно 1, 2 и 3. `date_from`/`date_to` = `YYYY-MM-DD`. `id` в теле. Окна дат. `pageSize` до 500 (у нас 100 — не менять в этом ТЗ). Конец: `count==0` или `received>=total` или `count<pageSize`.
- `pay/index`: `customer_id`, `page`, `pageSize` (у нас 50 = дефолт Alfa). `date_from`/`date_to` у **платежей** в доке `yyyy.mm.dd`, не `YYYY-MM-DD` уроков. Окно уроков в `pay/index` **не передавать** — 400 как у дат группы 568.
- `updated_at_from/to` у pay есть. В этом ТЗ полный скан по `customer_id`, не инкремент. Не делать.
- Филиал только в URL. 1–4 как сейчас.

## Зачем

`if (!balance)` — шаг 4 не ходит в `lesson/index`. `recheckDays` с экрана пустой.

Дыра прошлого ТЗ: «сначала окно журнала, потом касса» в одном вызове 90 с. Перепись 3 статуса × филиалы + missing 50 × статусы × филиалы при 5/с легко съедает 90 с. Касса (`PAY_INBOUND_RUN=4`, бюджет 20 с) не стартует. `paysRecheckAt` нет → синяя крутит того же, census каждый раз с нуля. Снова Крюкова.

## Шаг 1. Синяя `balance && recheck`

**Порядок в одном `pullOneStudent`:**

1. **Касса всегда первая**, как сейчас: `inboundCustomerPays` `{ force: true }`, курсор, 4 страницы / 20 с. `pay/index` **без** дат урока, **без** `recheckDays`. Типы 5/6/9 и `ctt_id` не трогать.
2. **Журнал окна — после кассы**, тем же `waitLockStudentAlfa(cid)`, пока есть остаток 90 с. Тот же блок шага 2 синяя: `recheckCensusWindow` ±N, `date_from`/`date_to` YYYY-MM-DD, статусы 1/2/3, prune в окне, missing, `keepAlfaProbe` / `windowAlfaKeep`, галка. Не 2015. Не полный fill. Нет даты — dropped. Не досидели missing — не ретраить очередь шага 4.

`shouldRetryOpenRecheck(balance)` только `!paysRechecked`. Не `!rechecked`.

`mark()` не пишет `paysAt` / `paysRecheckAt`. Их блок кассы после `scanDone`. `lessonsRecheckAt` — только если журнал окна закрыт по id. Checksum нет.

Вложенный lock не делать. `payFill` из журнала не сбрасывать. `pageSize` кассы и poll не менять.

## Шаг 2. Красная `balance && !recheck`

Касса первая, как сейчас. Вправо `paysScanned || pays`. Не ±1 ₽.

Журнал **после** кассы, **только если** `lessonsStampShort` и нет галки **и** остался бюджет: **одна** пачка missing (`dateFrom` YYYY-MM-DD, тела `{ id, status: 1|2|3 }`). Не fill. `shouldRetryShortPeople` для balance **не** включать.

Сошёлся или галка — `lesson/index` не звать. `setsClosed` false — в пачку, не skip (03f). После пачки не сидеть.

## Шаг 3. Не менять

`peopleJobFinished(balance)`, `skipLeads`, `shouldRetryCash` красной, один `crm-pays.json`, шаг 5, `PAY_INBOUND_*`.

## Критерий A

1. Тест: `balance+recheck` бьёт `pay/index` до `lesson/index`.
2. Тест: журнал не закрыт, pay `scanDone` → `paysRecheckAt` есть, очередь не ретраит по short.
3. Тест: в `pay/index` нет `date_from` из окна уроков.
4. Тест: `lesson/index` окна всегда с `status` 1|2|3, даты YYYY-MM-DD.
5. Тест: красная, журнал готов → только pay.
6. Тест: красная, short, нет галки → pay, затем не больше одной missing.
7. Тест: checksum на `paysRecheckAt` не влияет.
8. `admin-crm-settings.tsx` без диффа.

Простыми словами: шаг 4 сначала читает платежи (Alfa 5/с не отдаём журналу). Потом, если время осталось, сверяет уроки за ± месяц по номерам. Очередь кассы из-за дырки уроков не встаёт.
