3. API (свериться с докой в момент работы)

Метод: `POST /v2api/{branch}/customer/index`. branch ∈ {1,2,3,4} как сейчас на студии (новый id с branch/index этим шагом не открываем). Заголовок как у остальных вызовов.

Фильтры доки работают как **И**. Не слать `lead_status_id` / `lead_status_ids` в фильтре кнопок — пропадут лиды без этапа («Не разобрано», в кабинете null).

`is_study` в фильтре: 0 лид, 1 клиент, 2 клиенты и лиды. **Не слать `is_study: 2`**: это не архив и не значение карточки.

`removed` в фильтре (дока): 0 только активные, 1 активные и архивные, 2 только архивные. В **таблице полей сущности** Customer `removed` как поле выдачи не показан — в строке может не быть. Дефолт, если фильтр не слать, дока не фиксирует.

Тело **Клиенты** (как текущие кнопки вкладки, архив не должен течь):

```
{ "is_study": 1, "removed": 0, "page": N, "pageSize": 500 }
```

Тело **Лиды** (как доска и как пример доки `{"is_study":0,...,"page":0}` — **без removed**):

```
{ "is_study": 0, "page": N, "pageSize": 500 }
```

Закон студии, не выдумывать: живой тест `crm-leads-sync.test.ts` запрещает `removed` в запросе лидов — «Не разобрано» часто без поля removed и отваливается на `removed:0`.

После ответа лидов: строку с `removed === 2` (если поле **пришло**) не писать как активного лида. `removed === 1` в строке — как сейчас isCrmLeadRecord: не лид. Нет поля removed — это лид, если is_study=0.

- `page` с нуля. `pageSize` до 500 (схема интеграции; дефолт доки 50).
- Ответ: `{ total, count, page, items }`. Цикл: page=0…; стоп если count==0 или received>=total или count<pageSize. Offset во время выгрузки может сдвигаться — не «пропал из выдачи ⇒ стереть ветки у всех на диске».
- Лимит: **не более 5 запросов в секунду** на все методы студии (оферта + шапка API), **общий** лимитер, не щель 200 мс одного цикла и не второй sleep 5 с на человека. 429 → backoff.

Не звать: cgi, lesson/index, pay/index, customer-tariff, inbound шагов 1–5, lead-status/index (это ТЗ-5).
